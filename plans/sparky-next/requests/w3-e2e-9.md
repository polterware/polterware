# Investigate startup and performance budget violations

Owner: W3-POLISH / core owner / W3-PACKAGING. No budget change is requested.

The unsigned packaged desktop took 1193.071 ms from Electron launch to visible main content and onboarding, exceeding the 1000 ms conservative interactive startup check. This is a proxy, not an exact Chromium first meaningful paint measurement; the declared FMP budget remains unverified. Idle RSS was Main 151.484 MiB, renderer 109.359 MiB, core 46.125 MiB. Only core RSS has a declared limit (60 MB); it passed.

An earlier core run measured its first fresh-database startup at 1007.903 ms against 300 ms; the next nine starts were 29.296–35.113 ms. An earlier 10k FTS run, concurrent with desktop verification, measured p95 30.146 ms against 30 ms. These failures are retained even though the dedicated final run passed: list p95 15.995 ms, FTS p95 26.662 ms, fresh-database startup 27.714–102.822 ms. OS caches were not flushed, so fresh databases do not establish a cold filesystem cache measurement.

Evidence: `apps/sparky-desktop/test-results/perf-final/artifacts/perf-desktop-startup-and-idle-process-RSS/trace.zip`, its JSON reporter attachments, and `apps/sparky-desktop/test-results/go-perf.txt` (final core run). Earlier measurements are retained in `status/w3-e2e.md`. Environment: M1 Pro, 16 GiB, macOS 26.6.2, Electron 44.4.5, unsigned arm64 app.

Suspected areas: `apps/sparky-desktop/src/main/index.ts`, core startup/database initialization, and FTS query/storage implementation under `sparky/backend/`. These are investigation leads, not established causes. Measure true renderer FMP and clean-machine startup, explain the first-launch variance, and keep the existing budgets. The missing virtualized rows separately block meaningful scroll FPS measurement (request 3).
