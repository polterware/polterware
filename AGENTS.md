# Polterware Agent Instructions

## Communication and editing

- Speak to Erick in Brazilian Portuguese.
- Write code, UI strings, technical documentation, commits, logs, and identifiers in English.
- No Portuguese text anywhere in the repository: code, comments, UI strings, error and log messages, tests, fixtures and test data, docs, and skills are English only. Portuguese is only for chat with Erick.
- Preserve unrelated work and make the smallest safe change.
- Do not create branches or commits unless explicitly requested.
- Do not run browsers, previews, distributions, or development servers unless explicitly requested in the current task. Automated tests and builds may run by default.

## Work cards

- Codex and other agents: run `polterware format` once for the Polter core (Work cards; `polterware format structure|rules|feature|conflicts` for the rest), read with `polterware query cards`, and write Work cards with `polterware apply <file|->` (frontmatter `summary` and `rationale`). Claude Code gets the same through the `plugins/polterware` plugin (a symlink to `core/plugin`, which the binary embeds); `polterware setup claude|codex` installs it, and `polterware hooks enable|disable <name>` switches its hooks. The `context` hook (PostToolUse on `Read|Edit|Write|MultiEdit`) adds the brief of the Structure node a file belongs to once per session, again when that brief changes (`hook_context_seen`, because the core exits when idle); `polterware status` and its SessionStart hook add a line when the installed plugin or skill is older than the binary.
- Codex and other agents: start a session with `polterware status` and end it with `polterware handoff`.

## Product positioning

Polterware's category is **Project Context & Change Intelligence for AI Coding**: every agent and person reads the same project state, the Rules are the law agents read before they change anything, and each card shows the commits that did its work. The shipped wedge is Rules, the agent brief and search, Context Compiler, stable MCP reads, card Commits, AgentRun, audited MCP writes, CLI, Unified Change History, the Polter format with Work cards, Structure, Canvas, the Inbox, and the Rule lifecycle.

[`docs/future.md`](docs/future.md) is the only planning document and lists what is **not** implemented (Cloud, Jev, enrichment backlog, research). It is direction, not shipped behavior; never present its items as shipped. The code, this file, `polterware --help`, and `polterware format` describe what exists.

## Current product boundary

Polterware is both the umbrella and the main local-first app. Its Desktop is a GPUI app, `app` (Rust, on the shared [polterware/ui](https://github.com/polterware/ui) library), a client of the Rust core. The Electron Desktop is retired and gone from this repository; its last source, the reference for the look and behavior still being ported, is the workspace's `polterware-old` checkout. The repository is Rust only: no JavaScript, TypeScript, or Node tooling. The ecosystem's other apps live in their own repositories: Polterware Dispatch in [polterware/dispatch](https://github.com/polterware/dispatch) and Vitals in [polterware/vitals](https://github.com/polterware/vitals). Polterware's first version is a local SQLite-backed Desktop with project surfaces Inbox, Milestones, Structure, Canvas, Knowledge, and Activity. Project switching happens on the Projects screen, reached through the Home button in the title bar, before entering a project. Project settings is fixed in the sidebar footer; App settings is the gear next to Commander in the title bar. Inbox is the default route.

The umbrella is an ecosystem, not a list: apps and tools live under Polterware only when they can integrate with the others. See [`docs/ecosystem.md`](docs/ecosystem.md) for the admission criteria and the current roster.

The Desktop supports multiple local projects. It has no hosted or shared workspace model. One local core process (`polterware serve`) per database is the only process that opens SQLite (it is a detached daemon guarded by a lock, with a build handshake); The Desktop, the CLI, and the MCP bridge attach to it or start it. The Desktop reads and writes only through the core, over Connect-JSON (`app/src/client.rs`, which finds it through `<db dir>/run/core.json`). There is no TUI: `polterware` with no arguments prints its usage.

A project is a name, with no folder. Repositories belong to components, optionally (the `repositories` table: name, GitHub identity `github.com/owner/repo` from the clone's remote, and this machine's clone as `local_path`). A node's Checkout picks one or chooses a folder (Polter `dir: <clone>`, which creates or reuses the repository), several components may share one, and the last component to unlink a repository removes it; with exactly one repository a node with no `repo` uses it. `polterware init` links the folder it runs in as the first component (`--no-dir` starts empty), `polterware repo list` reads them, and the CLI finds the project of the current directory by its repository clones.

The coding agent tooling (MCP, setup, hooks, the skill, the CLI reference) and the local core live in App settings. Polterware has no environments, deploys, or platform connections.

## Polterware Dispatch

Polterware Dispatch, which delegates a task to a coding-agent CLI by difficulty and quota, is its own app and repository ([polterware/dispatch](https://github.com/polterware/dispatch)): its binary, core, desktop, contracts, and skill live there, and this repository holds no Dispatch code. What stays here is the integration:

- Contracts: Dispatch's protos are vendored in `schemas/vendor/dispatch` (its own buf module, excluded from the main one) and generate the Desktop's Rust in `app/src/dispatch/contracts` (`tooling/gen-contracts`). `bash tooling/sync-dispatch-proto.sh` copies them from a Dispatch checkout (`$DISPATCH_DIR`, else `../dispatch`) along with `schemas/polterware/local/v1/dispatch_host.proto`, then regenerates; `--check` reports drift without writing. Never edit the vendored files by hand.
- `DispatchHostService` (`dispatch_host.proto`) is implemented by the core here: Dispatch reads the projects, a run's directory, area, and card text, the open cards and repositories, and the AgentRun each run writes under.
- `app/src/dispatch` is the Desktop's Dispatch client, and `app/src/views/commander_route.rs` draws the route pills with the agent avatars of `polterware-ui`.

## Architecture boundaries

- Rust local authority: the single `polterware` binary (`core/src/runtimes/cli`: commands, `serve`, `mcp`) and retained domains only.
- Desktop: `app`, the `polterware-gpui` crate of the root Cargo workspace, on `polterware-ui` (interface work follows that library's `AGENTS.md`, Building interface: general components there, the Electron app's look on its tokens and materials, gpui-kit's behavior; no third-party GPUI kit as a dependency), a client of the core over Connect-JSON that never opens SQLite. What it lacks, in porting order, is in `docs/future.md`. It stays on the published gpui, never a patched, forked, or vendored copy: where the engine cannot do what Electron does, the GPUI Desktop adapts to it with the closest result the engine draws, and `docs/future.md` names the difference.
- App icon: `app/resources/polterware.icon` (the icon compiled into release bundles), `polterware-ice.icon`, and `polterware-fire.icon` (Icon Composer), `app/resources/polterware Exports`, and their 1024px macOS-grid PNGs (`app/resources/polterware-icon.png`, `polterware-ice-icon.png`, `polterware-fire-icon.png`) applied via `polterware_ui::window::app_icon::apply` at startup and from Appearance › App icon, as Dispatch and Vitals keep theirs.
- Contracts: `schemas` to the Rust contracts in `app/src/contracts` (`tooling/gen-contracts`), shared by the core and Desktop; `bash tooling/generate.sh` generates them. Never edit generated code by hand.
- The core uses a technical bearer session token without an account directory.
- There is one clean SQLite baseline and no compatibility requirement for earlier databases.

## Product navigation

- Agent reads: `polterware brief <card slug|Structure path|file>` (`polter.query "brief …"` over MCP) is the one read before work: the target with kind and technology then its Rules (the node's own, its ancestors' marked `(from <path>)`, and the whole project's, never cut by the budget and binding on agents), open tasks and questions, the last handoff, the card's invariants, the milestone goal, canvas links, and doc titles, in that order, deterministic and cut from the end to a token budget. A file resolves to the node with the longest `repo` + `path:` prefix. `polterware search <terms>` (`context` is an alias) lists matching nodes, cards, Rules, and docs one line each. The format is layered the same way: `polter.SpecCore` (about 360 tokens, declared in `SpecCoreTokens` and checked to 10%) is what `polterware format`, `polter.format`, and the plugin skill carry; Structure, Rules, the feature flow, and Conflicts are topics read on demand. `core/tests/integration_token_budget.rs` ratchets what agents read.
- Checkout projections: `polterware export` writes the generated block of each checkout's AGENTS.md (the Rules first, the project's and each applicable node's with `(from <path>)`, then the checkout's Structure nodes with kind and technology, and the `brief` line); it never reads them back. AGENTS.md sync is opt-in per project (`project_settings.agents_sync`, `polterware export --sync on|off`, `WorkService.SetAgentsSync`, or the switch in Project settings › General): the core rewrites only the block, only when it changed, a moment after a write that can affect it.
- MCP setup: `polterware setup mcp [list] [--json] | add | remove <claude|codex|cursor|all>` registers the `polterware mcp` server with Claude Code, Codex, and Cursor (`core/src/providers/agentsetup/mcp.rs`); App settings › MCP server shows each client and sets it up or removes it through that command.
- MCP: four tools. `polter.query` takes every `polterware query` read, including `show <id>` (one card, Rule, doc, entity, or run), `commits <slug>`, and `conflicts` / `conflict <slug>`; `polter.apply` writes Polter text; `polter.format` returns the core or a topic; `doc.upsert` writes a doc with a Markdown body. Writes join the session's AgentRun without a start or complete call, and a retired tool name returns an error naming its replacement. A Rule is a `#### rule <slug>: Statement` block with `scope:` (Structure paths; none is the whole project), an optional `why:` (Markdown, the lines after it), `status:` (proposed, active, under_review, replaced, removed), and `replaced-by:` (a Rule slug or id, which sets the status to replaced; it must name a live Rule and never the Rule itself); only active and under_review Rules bind. A node's `! text` line is a Rule scoped to that node. A retired `#### decision` or `#### fact` block answers with an error naming `#### rule`. A Conflict is a `#### conflict <slug>: <the request>` block with `rule:` (the law it goes against), optional `card:` and `options: a | b`; an agent raises one instead of acting against a Rule and goes on with work it does not block, `answer:` decides it and `status: withdrawn` drops it (`polterware conflict raise|decide|wait|withdraw|list`; `wait` blocks until a person answers, and `polterware status` lists the answers of the last day).
- Inbox: master/detail page of derived items, grouped by kind — Conflicts (a request an agent raised against a Rule; the detail shows the request and what it goes against, and Decide picks an option or takes another answer; `inbox.KindConflict`), Questions (open card questions) — with the active item's detail on the right, closed until a row opens it and closable, like Activity's (the first item starts active; J/K or a row opens it again, and a resolved item hands over to the next). H moves the active item or the selection to Later (`defer`) and D dismisses it (`ignore`); count in the sidebar, also in `polterware status` and `polterware inbox`. Selected items take an action they all offer (Later, Dismiss) at once. The UI uses plain words throughout: stage ids `shape|plan|build|verify|delivered` read Idea, Planned, In progress, In review, Done; Rule states `under_review|replaced` read Under review and Replaced; the section name is Knowledge (route `truth`); ids, Polter keys, and the CLI keep their names.
- Milestones (the `milestones` route, formerly Work; `work` redirects): each milestone is a board of Work cards, with Board and Specs as its layouts
  - The section opens on the Roadmap, a table of the boards with no tabs: All cards (every card of every board) first, then the milestones in order with state, delivered/total progress, and target date. A row opens that board, a route of its own (`ClientRoute.milestone`, remembered per section): its toolbar has Back and the Board and List tabs at the start and the actions at the end. Cards with no milestone are in All cards (grouped by milestone, the List shows them under Backlog). A milestone is `milestones` (slug, name, goal, exit criteria, target date, state planned|active|done), and a card belongs to at most one (`work_cards.milestone_id`); Board and Specs (the List, switched with those tabs or Cmd+B) show the open view's cards grouped by stage, and M (or the List's selection toolbar) moves the focused card or the selection to a milestone in one write. Milestones are created (in the shared `Composer`: the name, the goal, the state, and the target date), renamed, reordered, and archived in the Desktop or with `polterware milestone new|set|order|archive|restore` (`WorkService.*Milestone*`); archiving moves its cards to the Backlog. Polter assigns a card with `milestone: <slug>` (empty returns it to the Backlog), and agents read `polterware query milestones|roadmap` (roadmap lists the active ones with goal, exit criteria, and open cards).
  - The Polterware store, not Polter text, is the source of truth; `.pw.md` files are input only.
  - Board groups Work cards (`work_cards`) by stage (Idea, Planned, In progress, In review, Done; ids `shape|plan|build|verify|delivered`). A card ends with its Tasks row (done/total), a `Morph` that grows into the card's task list, where the shared `Checkbox` checks a task off or opens it again (a `- [x]|[ ] T<n>` line, no why asked). The Desktop reads through `WorkService.ListWorkCards` and writes Polter text through `WorkService.ApplyPolter`; agents use `polterware apply`.
  - A card opens as a page (`WorkCardDetail` on `RailPage`) whose column holds, after its intent: its Tasks and Invariants, the next stage gate (Contract gate in shape, Plan gate in plan) with the review checks that hold it and the button that passes it inline (`WorkService.AdvanceFeature`, no why asked; a refusal stays as error lines), Verification (`WorkService.VerifyFeature`, read-only), Commits (`WorkService.ListCardCommits`: the commits whose message cites a task as `slug#T2`, `slug T2`, or `polter: slug#T2`, read from the checkouts' Git, plus the ones linked by hand in `work_commit_links`; each row has the subject, the task, the short sha, a GitHub link built from the checkout's `origin` remote with plain git, and × on a linked one; its "+" links a sha to a task in a `Morph`; commits are optional and raise nothing in the Inbox; agents link one with `polterware task done <slug>#T<n> --commit <sha>` and read them with `polterware query "commits <slug>"`), the last handoff for the card (from `ListAgentSessions`), the dispatch runs that name it (from Polterware Dispatch; a row opens the run there), and the Agent brief (`polterware brief <slug>`) with Preview and Copy; then its Activity. Its Tasks section checks a task off or opens it again with its box, and drops an open one with × (a `- [x]|[ ]|[-] T<n>` line, no why asked). The new-feature flow only creates cards.
  - Specs is the List of the same cards (Cmd+B switches it with the Board): grouped by stage or milestone, ordered, and with the properties the Display section at the end of its filter menu shows; selected cards move to a stage or archive in one write under one justification. The five-document Spec / Plan / Tasks / Clarify / Checklist model and the Constitution document are removed; a Rule with no scope holds for the whole project.
  - A card's Polter text carries the spec-driven flow: `behavior:` says what it does (Specify), `edge-cases:` the cases it must handle, `plan:` its architecture, APIs, and files touched (Plan), the `- [ ]` tasks are the work (Tasks, Implement), and `confirm: ! <criterion>` or `confirm: rule <slug>` records what was checked (Analyze), which `polterware verify <slug>` lists as pass or check. Each of the three sections keeps the lines after it as a Markdown body; a body ends at the next section, at a `#` or `##` heading, or at a `#### rule` / `#### conflict` block, so `###`–`######` headings, `!` lines, `?` questions, and checklists inside it stay text (write the tasks, questions, and invariants before the sections); a Rule's `why:` body ends at the next `#` to `####` heading.
- Structure: registry of the project tree: the project, its domains, and components under a domain or loose under the project (`structure.Levels`; there is no system level and no subdomain; a feature is a Work card linked to a node). A domain only organizes components: only a component has a checkout (repository and folder), and Polter refuses `repo:` or `path:` on a domain. A compact branch tree on a card on the left, hidden and shown from the toolbar's sidebar button, with its own search and filter (level and component kind; F) at its top that keep the ancestors of each match, the active filters showing under the toolbar, (texture +/- keys with curved guides) whose rows are one line: a tile with the level's glyph, the title, and on hover, Add domain on the project and Add component on a domain. Selecting a row (click or arrow keys) shows the node as a document on the right, with no global panel, laid out like a project overview and edited in place: a kind tile, the title and the description as summary (inline fields; the project's document edits the project's name and description), and the level beside the kind tile (the document has no actions menu: adding is on the tree's rows and moving is the Domain picker) (a picker where a node right under the project with no children may switch between domain and component; becoming a domain clears its kind and checkout); then, on a component only, one labeled line per field, in groups set apart by a rule: what it is (Domain, the picker that moves it; Kind and Technology, each a list of tokens edited like the filter's, in the shared `TokenPicker`: Kind from the component kinds, Technology from the project's technologies or any typed text), where its code lives (Repository, the picker listing the project's repositories with the GitHub mark and owner/repo when the remote is GitHub, plus Choose folder…, and a GitHub button that opens it; Folder, the path inside it); then collapsible sections, flat on the page with a larger heading (no icon tile, no count, the fold chevron right after the title) and a table: the Rules that hold for it (its own, then its ancestors' as From <node> and the whole project's), and every card, Rule, and doc that cites it, whose rows open the record for editing in the Composer that creates it (`RecordEditor`), with Expand to its page for a card, Rule, or doc (a Rule has no page, so no Expand; a page's Back closes to its own list): a section's + links one more (a card goes under the component; a Rule or doc gains the node among its contexts) and a direct link's × unlinks it (removing only this node from the contexts; an inherited Rule has no ×); a node's document ends with its Activity. Structure is the tree alone: a node declares no dependencies (`uses:` is retired), because how the parts relate is drawn on a canvas. The toolbar holds only the tree toggle, with no search, filter, or add button, and floats on the toolbar's fade over the document scrolling under it; every dropdown on the page shows icon tiles; branches open and close on the shared springs and fade as they go; a component's `kind:` lists canvas component kinds (`structure.ComponentKinds`, comma separated) and `tech:` lists technologies in free text, comma separated (a canvas draws the first kind). Structure is the only name for the project tree (the CLI command, the Polter query kind, the store tables, and the route).
- Canvas: many canvases per project, all of one generalist type (`canvas`). It mixes drawing shapes (general and flowchart shapes, frames, notes, text) that carry no meaning with semantic components (a kind such as web app, service, database, cache, queue, AI model, or team, plus a free-text technology and an optional Structure link; a linked Structure node's title, kind, and technology win over the canvas values, in the Desktop and in the agent export); domain and component nodes must reference a Structure node. The editor has a shape library on the left and a fixed inspector on the right. A canvas is Mermaid source, and its layout (positions and viewport) is stored separately with the positions people set pinned. Agents read it (`polterware canvas ls|show`, `polterware canvas save <id|name> --source <file|->`, MCP `polter.query` kind `canvas`, and `polter.apply` with `canvas: <name|id>`) only when it is marked agent-visible. Every node keeps its id, kind, label, ref, and props in a Mermaid `@{ }` block and every link its id and kind, so the text reads back as the same graph and a write whose text does not parse answers with its line and column. A node drawn inside another sits in its subgraph, so frames become subgraphs; components show kind and technology but not style; nodes with no ref are listed in an `unverified` class line; and `canvas show --format json|dot` keeps the other shapes. Free items can be promoted to Work cards and Rules.
- Knowledge (the `truth` route): Rules, Docs
  - Every Knowledge and card table shows a Context column of node chips ("Whole project" when empty; a card's is its component), and detail pages name the same property Context.
  - Rules are the law agents read: the statements the code must keep (the `rules` table, `WorkService.ListRules`), each holding for the Structure nodes it names and everything under them, or for the whole project. The list (Rule, Holds for, Status) has a lifecycle filter (Proposed, Active, Under review, Replaced; all states shown by default) and opens a Rule as a page with its statement, Context, Status, Why, and Activity. Only active and under review Rules bind; `replaced-by:` names the Rule that replaced it, and `Decision-NNNN` still resolves as an alias of a migrated Rule. Writes are Polter rule blocks.
  - Docs is one list of docs (knowledge `kind = doc`) with no type: every doc is the same kind of page, and tags are the free labels people sort and filter them by (`doc_type` is always `doc`; the retired `runbook` type became a `runbook` tag). Docs and Rules are about a list of contexts, Structure nodes picked as chips like filter tokens (the shared `TokenPicker` as the Composer's Context property and in the detail rails; "Whole project" only when the list is empty); there are no separate entity links on them. Docs hold only what lives in Polterware: repository files are not registered as docs (the `source` type is retired, archived, and refused with an error), because agents read them from the checkout and Structure checkout paths already tie code to project parts.
  - Resources are Structure components; there is no separate Inventory surface.
- Agents: Polterware has no Agents section; running coding agents belongs to Polterware Dispatch (above). The Desktop's Dispatch client (`app/src/dispatch`) attaches to the `dispatch` core through its `run/core.json`, or starts it when the app is installed: a card's page lists the runs that name it, Activity lists the dispatch entries, and Commander's run and Send this card to an agent start a run through Dispatch's core; the run then opens in Polterware Dispatch through `dispatch://run/<id>`, its only link. Each of them hides while Polterware Dispatch is not installed. Polterware serves Dispatch through `DispatchHostService`: the projects, a run's directory, area, and card text, the open cards and repositories, and the AgentRun each run writes under. `polterware run|runs|wait|result|cancel|merge|route|tiers|usage|…` runs `dispatch <command>` when it is installed and otherwise names it; the store keeps no dispatch tables but `dispatch_tiers`, which Dispatch copies on its first start.
- Activity: the Unified Change History of justified changes across every surface (canvas edits stay audited but are not listed, except a changed relation: an edge added or removed between two nodes that cite Structure nodes is listed as Connect or Disconnect and joins both nodes' Activity, `canvas.RelationChanges`), plus dispatch history entries (started, merged, failed) read from Polterware Dispatch, in a 44px table grouped by day (Today, Yesterday, the weekday, then the date) and filterable by person, agent, and tier. It has no data of its own. Every document (doc, Rule, Work card, Structure node) ends with its own Activity: the changes that named it among their subjects (`ListChangesRequest.subject_id`), newest first, with who made each and why. Opening a dispatch entry shows a summary and opens the run in Polterware Dispatch, not the live log.
- Creating: every new card, Rule, and doc opens in the shared `Composer` (title first, description, property pills, an optional Why; Cmd+Enter creates, Create more keeps it open). C opens it for the open surface, and a column's or group's "+" opens it with that stage or milestone set; a milestone board has no toolbar +. New and renamed canvases use it too, and so do new domains and components (the project takes a domain, a domain a component, with a Domain pill), promoting a canvas item to a card or a Rule. Reasons: a person may leave the rationale empty (the core checks it per actor with `agentrun.ValidateChangeAs`; Activity shows "No reason given"), while agents must give one. The Desktop never asks a person why: moving a card back a stage and moving a Rule to under review happen at once, and archiving cards or docs and replacing a Rule are confirmed with no reason asked.
- Settings is one dialog with a grouped rail, opened in one of two scopes:
  - Project settings (sidebar footer): Project (General — with the AGENTS.md sync switch, Danger zone — archive project).
  - App settings (title bar, next to Commander): Agents (MCP server and its clients, Agent setup, Hooks, AI skill, CLI reference) and App (Shortcuts, Appearance, Local core, Danger zone — reset local store)

Removal is soft: docs and canvases are archived (`archived_at`; hidden from lists, search, context, and agent reads, restorable from each surface's Archived view), and Work cards and Structure nodes keep `status = removed`. The core permanently deletes only an archived item and never a Rule; a Rule moves through its lifecycle instead.

Scope is a global filter, not a surface: each scoped page edits the one shared selection from its PageToolbar filter menu, with repeatable tokens (`domain:`, `component:`, and `env:` on Knowledge Docs and Activity; Structure always shows the whole tree and has no filter). Node tokens are one union sent as `scope_nodes` (a parent includes its children; ancestors stay included because the read is non-exact). It narrows Work cards (through their component), Rules, Inbox, Activity, the Context Compiler, `polterware query|status|inbox|search --scope <node> [--exact]`, and the MCP `scope` argument. An entity has any number of contexts (the `entity_contexts` table, `scope_node_ids` in the contracts); a filter matches it when any context matches, and none means the whole project and stays visible under any filter. Rules take `scope: a, b` in Polter, and a Rule with none holds for the whole project. `polterware scope <kind> <id> [<node>...]` replaces the contexts, and derived Inbox items are scoped with `polterware scope item <key> <node>...`.

While a Work card is open, Commander lists Copy agent brief (`polterware brief <slug>` to the clipboard) and Send this card to an agent (a run on the card through Dispatch's core, on the route Commander's pills hold, then opened in Polterware Dispatch; it names the install when Dispatch is missing) first.

Keep history controls, the Home button with the breadcrumb after it (the project, whose crumb opens Switch project: a search, each project on its folder tile, and New project; then the list you are in, a tab of its own such as Rules or else the section, with no section group; then what is open in it, cut with an ellipsis: the milestone board, the canvas, or the card, doc, or Rule; the list crumb and a board under an open card navigate back), Commander (its input also takes an agent prompt: it has the Composer's frame (its width and Close) and its input is set like the Composer's title, with no leading icon and no divider (the results fade at their top edge); a query that matches no command reads as a run laid out like a Composer: the list goes away and the panel glides to the run's height, then the details, the Route, Milestone, and Card pills, and Start run; Enter runs a matching command or, in a run, moves to the details, and Cmd+Enter always starts it, at once, on those pills (from `@polterware/feature-dispatch-link`; the open card comes preset), started through Dispatch's core, and the run opens in Polterware Dispatch; without Dispatch, a query that matches no command is only a search), App settings, and Project settings. Project switching happens on the Projects screen; do not introduce additional product surfaces without an approved Rule.

## UI law

`DESIGN.md` and `polterware-ui` are the visual source of truth (the Solid design system they came from is in `polterware-old`). Product features must use shared `Input`, `Textarea`, `Select`, `Field`, `Button`, `Card`, `Surface`, the shared overlays, `PageToolbar`, `FilterChip`, `DataTable`, `IconTile`, `StatusChip`, `EntityMenuButton` with `EntityContextMenu` (one action list for "…" and right-click), `PropertyPicker` (in a row, `PropertyPills`), `TokenPicker`, `RadioGroup`, `OptionTile` (leading every option of a list in a popover), `Morph` (a button that turns into its own confirm), `Peek`, `HoverCard` (a preview a long hover opens), `EntityNavigator`, and the global `DetailPanel` where applicable.

Prefer minimalist icon-only buttons with the shared tooltip over text buttons in toolbars and page chrome; see `DESIGN.md`.

Do not hand-roll shared control chrome, menus, dialogs, operational tables, or entity panels. Use only radius and color tokens. Structural surfaces and text are opaque; alpha is limited to shared border, shadow, scrim, and transition tokens. Exception: on macOS the main window title bar and sidebar may use window vibrancy with the shell glass washes; Commander and other product chrome stay opaque. Hugeicons Free Stroke Rounded is the only product icon set.

## Verification

After relevant changes, run the static checks (`cargo fmt --check`, `cargo clippy --all-targets`, `buf lint`, `git diff --check`) and the tests that cover the change (`cargo test`); `bash tooling/verify.sh` runs them all. Maintain risk-proportional tests.

Do not add Markdown design or planning documents. Record Rules and work in the Polterware store (`polterware apply`); put unshipped direction in `docs/future.md` and delete items from it when they ship.
